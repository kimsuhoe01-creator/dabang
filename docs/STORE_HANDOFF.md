## 2026-08-30 CUKCUK 실제 테이블 QR 경로 기본 적용 완료

- 일반 POS 주문과 배달 주문은 주방 영수증이 정상 출력되지만, 기존 태블릿 주문은 OpenPlatform `orders/create`로 테이블에 직접 등록되어 주방 전송 이벤트가 발생하지 않는 현장을 확인했다. 현재 프린터 이름·드라이버·매장 출력 설정 문제로 보지 않는다.
- CUKCUK가 실제 테이블 QR에서 사용하는 순서를 읽기 전용으로 확인했다: `GetOrderByTableID` → 메뉴 상세 조회 → `self-order/update-cart` → `self-order/confirm-order`.
- 먼저 URL에 `transport=cukcuk-self-order`가 있을 때만 위 실제 QR 경로를 쓰도록 시험 기능을 추가했다. 현장 시험에서 POS 기기와 관리자 태블릿 모두 주문 알림을 정상 수신했다.
- 일반 메뉴와 돈까스 플레이트 옵션 메뉴를 대상으로 실서버 테이블·메뉴 조회 드라이런을 통과했다. 드라이런에서는 마지막 장바구니 전송·주문 확정 호출을 가짜 응답으로 차단해 실제 주문을 만들지 않았다.

- 주방 영수증은 CUKCUK 관리자 확인 뒤 출력되는 매장의 기존 운용 흐름이며 사용자가 중복 재검증을 생략했다. 앱 쪽 검증 완료 기준은 POS 기기와 관리자 태블릿의 정상 주문 알림 수신이다.

## 2026-08-30 옵션 주문·사포로 수량·주방 출력 확인

- 옵션 메뉴가 주문 전에 HTTP 400으로 거절되던 직접 원인을 수정했다. CUKCUK 동기화가 만드는 정상 옵션 템플릿 ID `cukcuk-detail:<UUID>:0`의 콜론을 주문 Worker가 잘못 금지하고 있었다. 메뉴별 공개 템플릿 목록과의 정확한 일치 검증은 그대로 유지한다.
- 돈까스 플레이트, 윙봉 떠까, 반반 윙봉, 튀김, 사리 추가, 사포로 생맥주처럼 CUKCUK 옵션을 쓰는 메뉴가 수정 대상이다. 공개 카탈로그의 실제 옵션 ID를 기준으로 검증하는 회귀 테스트를 추가했다.
- 사포로 생맥주 `A02`는 330cc·640cc·3300cc 각각에 독립적인 `− / 수량 / ＋` 선택을 제공한다. 한 용량 이상을 골라야 담을 수 있고, 용량별 수량은 별도 주문줄로 POS에 전달된다. 같은 용량을 다시 담으면 기존 줄에 합쳐지며 용량별 최대 수량은 99개다.
- 사용자 현장 관찰처럼 옵션 없는 메뉴는 POS에 등록될 수 있으나 주방 영수증은 별도 CUKCUK 단계다. 테이블 QR 주문은 직원이 POS의 온라인/테이블 주문에서 `Xác nhận`한 뒤 `Gửi bếp/bar`해야 주방·바로 전송된다. CUKCUK 공식 안내상 이 확인 단계의 자동 처리는 지원되지 않는다.
- `Xác nhận` 후에도 출력되지 않으면 `Danh mục → Bếp/Bar → Chọn món` 또는 메뉴의 `Chế biến tại`에서 주방 배정을 확인한다. 이어 출력 담당 POS 한 대의 `☰ → Thiết lập → Máy in và mẫu in → Bếp/Bar`를 확인한다.
- 진단 기록을 켠 매장 POS에서는 `Lịch sử gửi bếp/bar`의 `Chưa gửi`와 `Đã gửi`를 확인한다. `Chưa gửi`면 주문은 생성됐지만 주방 전송 전이고, `Đã gửi`인데 종이가 안 나오면 POS·프린터 연결 또는 출력 담당 설정 문제다.
- 주문 완료 문구도 POS 등록과 직원의 CUKCUK 확인·주방 전송을 구분하도록 한국어·베트남어·중국어·영어로 수정했다. 앱이 주방 자동 출력까지 완료했다고 오해할 문구는 제거했다.
- 기능 커밋: `b7b8175` (`Fix option orders and add Sapporo quantity controls`), 자동 CUKCUK 동기화 커밋: `d9947bf` (`Update CUKCUK published data`). 동기화 실행 `33317701834`가 성공했다.

- 전체 회귀 테스트 52개, 메뉴 이미지 감사, JavaScript·JSON 검사, `git diff --check`가 모두 통과했다. 메뉴 112, 이미지 매핑 133, 이미지 파일 161, 누락·고아 0이다.

## 2026-08-30 실주문 400·전송중 안전 수정

- 현장 테스트 장바구니가 `전송 중…`에서 멈춘 시각의 Cloudflare 실시간 기록을 확인했다. 네 번의 POST가 모두 0.2초 안에 HTTP 400으로 끝났으므로 CUKCUK/POS가 느린 현상이 아니라 주문 Worker의 사전 검증 거절이었다.
- 같은 시각 CUKCUK 오늘 주문을 읽기 전용으로 대조했으며 화면 합계 `2,279,200 VND` 주문은 0건이었다. 실패한 테스트 주문과 중복 주문은 POS에 생성되지 않았다.
- 원인은 실주문 화면도 브라우저의 과거 편집용 `dabangTabletPreview` 데이터를 읽어 최신 공개 메뉴와 다른 옵션을 보낼 수 있었고, 화면은 서버의 구체적인 거절을 표시하지 못하던 구조였다.
- 실주문 모드는 이제 로컬 편집 초안을 완전히 무시하고 공개 카탈로그를 불러오기 전에는 담기·전송을 허용하지 않는다. 카탈로그 revision이 바뀌면 주문 서버가 POS 호출 전에 명확히 거절한다.
- 주문 화면은 동기 예외를 포함해 항상 `전송 중…`을 종료한다. 20초 안에 결과가 없으면 재전송을 막고 `POS 확인 필요`를 표시하며, 확실한 4xx 거절은 `POS로 전송되지 않음`과 새로고침·재선택 안내를 표시한다.
- 각 장바구니에 안정적인 `clientOrderId`를 붙이고 Durable Object에 처리 중·완료·결과 불명 상태를 기록한다. 같은 주문 ID는 CUKCUK에 두 번 보내지 않으며, 다른 장바구니가 같은 ID를 재사용하면 차단한다.
- 주문 Worker 배포 버전: `d2004d71-1aca-42cd-a3cc-2fdaf92790be`; `/health`는 `ok:true`로 응답했다.
